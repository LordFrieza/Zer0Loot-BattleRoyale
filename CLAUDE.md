# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Zer0Loot Battle Royale : un mini-jeu relié au chat Twitch (`!join` → combats automatiques → coffres de loot). Backend Node/Express + Socket.IO + tmi.js, frontend en JS pur et fichiers statiques (pas de build, pas de framework). L'interface, les commentaires et les textes du jeu sont en **français** : garde cette convention. `README.md` décrit toutes les règles du jeu, les variables d'environnement et les pages ; `DEPLOIEMENT.md` explique la mise en ligne sur Fly.io (`fly.toml`).

## Commandes

```bash
npm install
npm start                       # node server/index.js → http://localhost:3000
npm run dev                     # node --watch
npm test                        # node --test test/*.test.js
npm run test:coverage           # tests + couverture de code
npm run spec:coverage           # exigences de SPECIFICATION.md sans test
node --test test/bets.test.js                       # un seul fichier de tests (un par domaine)
node --test --test-name-pattern="BET-7" test/*.test.js   # un test précis, par identifiant de la spec
```

Développement local sans Twitch : `TWITCH_CHAT_DISABLED=1 npm start`. L'admin par défaut est `admin`/`admin` (interdit avec `NODE_ENV=production`). La page admin permet d'ajouter des bots et de simuler un `!join` pour tester. Il n'y a ni linter ni étape de build.

## Architecture

- **`shared/rules.js`** est un module UMD chargé à la fois par Node (`require('../shared/rules')`) et par le navigateur (`/shared/rules.js` → global `Rules`). Il contient *toutes* les formules d'équilibrage : stats, classes, raretés, table de loot, forge, récompenses, courbe d'XP. Modifie l'équilibrage ici, et garde-le sans dépendance à Node ni au DOM. Les tests de `test/` le couvrent : mets-les à jour quand les règles changent.
- **`server/index.js`** — routes Express (sessions par cookie `zl_session`, mots de passe scrypt, OAuth Twitch, endpoints admin) et hub Socket.IO. Il relie les autres modules : événements de bataille → récompenses (`game`) → rooms socket par utilisateur (`user:<id>`) qui émettent `me`, `reward`, `bet` ; diffusions globales `queue`, `frame`, `leaderboard`, `twitch`.
- **`server/battle.js`** — `Battle` (EventEmitter), machine à états `idle → queue → ready → battle → ended`. Le combat est simulé **côté serveur** à pas fixe (`TICK_MS`) et diffusé en `frame` ; les clients ne font que l'affichage. La zone qui se referme et les événements (brouillard, météores, mode rapide) sont ici, ainsi que les huit **modes de jeu** (`this.mode`, choisi à l'ouverture de la file) : `br` (chacun est sa propre équipe), `koth` (Roi de la Colline : chacun pour soi, colline mobile `this.koth`, points `score`, réapparition `respawnAt`, fin au temps), `clans` (Guerre des clans : équipes `clan` rouge / bleu choisies dans la file, cristaux `this.clans.crystals` qui tirent, réapparition de plus en plus longue, résultat `clansEnd`), `gold` (Ruée vers l'or, mode bonus sans combat : `tickGold()` remplace le combat, pièces / coffres / bonus dans `this.gold`, résultat `goldEnd`), `boss` (équipe `heroes` contre le boss choisi par l'admin, `this.bossId` : Troll, Dragon, Magicien, Mimic, Liche, Maexxna, Ether, Lilith ou Daedra, créé par `spawnBoss()` ; attaques spéciales annoncées dans `slams` (effets `bleed`/`poison`/`slow`/`stun`/`web`/`leap`), grandes étapes du `script` selon la vie : vol, nid, bouclier, illusions, copies du Mimic (`spawnCopies`), phases de la Liche (`licheChill`/`licheRaise`, gel `iceUntil` via `updateFreeze`), cocons, plafond et frénésie de Maexxna (toiles `this.webs`), intangibilité et mains spectrales d'Ether (`startIntangible` / `spawnHands`, feux follets, `startFury`), illusions / disparition / bonneteau / chapeau / neuvième vie de Lilith (`startIllusions`, `updateVanish`, `doShuffle`, `spawnHat`, `nineLives`), colonnes et cercles de feu infranchissables de Daedra (`this.firewalls`, `firePillar()` / `updateFirewalls()`), démons, portails (`guardMult`) et embrasement ; créatures ajoutées dans `adds` ; `immune()` décide qui peut toucher qui — un héros gelé ou dans un cocon est intouchable), `rush` (Boss Rush : `this.rush`, étapes `intro → fight → down → poll`, `nextRushBoss()` avec `Rules.rushScale`, vote via `openRushPoll()`/`closeRushPoll()` partagé avec le sondage du donjon par `pollHost()`, événement `rushBossDown` à chaque boss), `tourney` (Tournoi : arbre `Rules.tourneyBracket` construit au lancement par `setupTourney()` — paires par puissance, 1v1v1 des trois derniers si impair —, `this.tourney` avec étapes `bracket → fight → result`, un match à la fois dans `this.fighters` (`startTourneyMatch()` : pleine vie, `boost` du plus faible du match à partir de `baseHp` / `baseDamage`), zone `tourneyStorm()`, `endTourneyMatch()` qui fait monter le vainqueur dans le slot du match parent, `finishTourney()` → événement `tourneyEnd` ; l'arbre public passe par `publicQueue().tourney`, pas par les frames) et `dungeon` (salles successives, étapes `dark → enter → fight → clear → exit`, avec une étape `poll` de 60 s après chaque salle de chef : sondage du chat, votes via `battle.vote()`). Le ciblage et les dégâts de zone se basent sur `team` ; la taille au sol sur `r`. Effets temporaires (potions, ultimes) : `buffs` + `buffMult` / `buffSum` ; impacts différés : `zones` ; ultimes : `castUlt` quand la barre `stamina` est pleine. Le mode entraînement crée une `Battle` séparée par joueur (`trainings` dans `index.js`), sans écouteurs de récompense. Le **mode Solo** (V2) aussi : `new Battle({ solo: { kind, level, difficulty } })` (map `solos` dans `index.js`, événements `soloQueue` / `soloFrame`, 1 énergie par Expédition, 1 Clé de boss `bossKeys` par Défi des boss — clés trouvées via la relique rare `cle_boss`) ; `kind: 'expedition'` réutilise le mode `dungeon` avec `Rules.expeditionRoom/expeditionMultipliers`, l'étape `relic` (`openRelics()` / `chooseRelic()` / `applyRelic()`) à la place du sondage, et `kind: 'boss'` le mode `boss` avec `BOSS_SOLO_SCALE` × `BOSS_CHALLENGE[difficulté]` (difficultés ultimes Fabuleux / Mythique / Divin, `ultimate` : attaques spéciales `special`, `attackSpeed`, `enrageAt`, soins du héros `healTaken` ; créatures en √vie et dégâts^0,7 ; `Rules.challengeRank` pour les compteurs « ou plus ») ; vitesse ×1/×2 via `setSpeed()` / `loopStep()`, `abandon()`. **Style de combat** (V2) : récupération immobile après chaque attaque (`recovery` / `recoverUntil`), recul qui longe les murs (`retreat()` / `escapeSpot()`), tactique (`stance`, `targetPref`, `kite`) et techniques signature (`techs`, `useTechniques()` / `attackTechniques()`).

- **`server/casino.js`** — casino : neuf jeux payants tenus par les boss en smoking (`Rules.CASINO`, fonctions pures `slotsPayout`, `rouletteWins`, `bjValue`, `glaceMult`, `heavenMult` / `heavenCrash`, `chatonMult`, `courseChances` dans `rules.js`). Road to Heaven (point d'effondrement secret, temps du serveur ; `/heaven/check` interrogé en boucle sans sauvegarde tant que rien ne change) et Chaton Fripon gardent leur partie en session comme le blackjack ; Course de démons en un appel. Tickets de casino (`character.casinoTickets`, Mini Lilith) : paramètre `ticket`, mise de 50 golds payée par le ticket (`checkBet` / `take`), jamais à la caisse. Tirages `crypto` ; la mise est retirée au début du coup, les gains crédités à la fin (statistiques `casinoBets` / `casinoWagered` / `casinoWon` / `casinoBest`, compteurs `casinoPlays`, `jackpots`, `casinoLegend`). Blackjack, Lac gelé, Road to Heaven et Chaton Fripon gardent leur partie dans `db.state.casino.sessions[userId]` (carte cachée et fissures jamais envoyées : `sessionsOf()` renvoie la vue publique) ; gros gains dans `db.state.casino.feed`, diffusé par l'événement socket `casino`. Routes `/api/casino*` dans `index.js` (`casinoAction`).

Le navigateur envoie sa position par socket (`sv:pos` → `input()`, bornée par `setPos()`) ; `tickAll()` (branché par `survivorTick` dans `start()` d'`index.js`) fait avancer toutes les parties, met en pause sans nouvelles du joueur et émet `svFrame` / `svEnd`. Lieux-dits à effets (`Rules.SURVIVOR_ZONES[…].fx`, combinés par `Rules.survivorZoneFx` avec la bénédiction d'autel) et exploration dans `updateExplore()` (autels, éclats d'émeraude, trésor gardé : `Rules.SURVIVOR_EXPLORE`, gardiens marqués `guard`). Terrain : `Rules.survivorGround` (eau ×0,5, route ×1,1). Montre (`slowUntil`, `timeMult()`) et Bombe (`bomb()`) ; Ether, Lilith et Daedra (`bossCombo()` : attaques à tour de rôle, intangibilité `ghostUntil`, esquive `dodge`, illusions `decoy` dessinées comme le boss via `b.decoys`, colonnes de feu `firewall` infranchissables par `Rules.survivorWallBlock` côté serveur et navigateur) ; évolutions (`Rules.SURVIVOR_EVOLUTIONS`, `evolve()` au coffre, pause `cine`) ; gardiens légendaires (`lairs`, `updateLegends()` / `legendAttack()`, ennemis marqués `legend`) ; sanctuaires (`shrines`, `curses`), `encircle()`, chariot (`cart`, `moveCart()`) ; jour/nuit `Rules.survivorDaylight` (rendu `drawDaylight()` du navigateur) ; armes secrètes (`Rules.SURVIVOR_SECRETS`, progression `survivor.secrets`) et défis du jour (`Rules.survivorChallengesOf`, `survivor.challenges`) crédités par `finish()`. `finish()` crédite émeraudes, récompense du jour (vague 30, `parisDay`), record, historique et statistiques ; `refundActive()` rend les golds après un redémarrage (`survivorActive`). ## Spécification détaillée

[SPECIFICATION.md](SPECIFICATION.md) décrit le comportement implémenté au format **EARS** (exigences numérotées : `ACC-`, `Q-`, `B-`, `BET-`, `FRG-`…). Lis-la avant de modifier une règle de jeu, et mets-la à jour dans le même changement.

## Cycle d'une partie (vue d'ensemble)

1. L'admin choisit le mode (et le boss) et ouvre la file (`/api/admin/queue/open`, 10 à 3600 s, `mode`, `boss`) → phase `queue` ; les viewers tapent `!join` (ou `!rouge` / `!bleu` en Guerre des clans, ou cliquent « Rejoindre »). Les paris sont ouverts en `queue` et `ready` dans les modes où l'on s'affronte (Battle Royale, Roi de la Colline, Tournoi — sur le champion, Guerre des clans — sur une équipe) ; jamais en coopération ni dans le mode bonus.
2. Fin du minuteur ou fermeture manuelle → `ready`. L'admin lance la partie (≥ 2 combattants en Battle Royale, Roi de la Colline, Tournoi et Guerre des clans, ≥ 1 en coopération et en Ruée vers l'or) : les stats des humains sont **recalculées au lancement** (`refreshParticipant`) → `battle`, paris fermés.
3. Tick de 50 ms : ciblage, déplacement, attaques, zone (dès 45 s, Battle Royale), événement éventuel, attaques du boss ou étapes du donjon ; chaque tick diffuse un `frame`. Battle Royale : fin quand il reste ≤ 1 combattant ou à 300 s ; Roi de la Colline : à 150 s, meilleur score ; Guerre des clans : cristal détruit ou 180 s ; Ruée vers l'or : 75 s ; Boss : boss mort, tout le monde mort ou 300 s ; Donjon : tout le monde mort.
4. `kill` / `streak` / `end` (Battle Royale ; seulement `end` au Roi de la Colline), `tourneyMatch` / `tourneyEnd` (Tournoi : gains `Rules.tourneyReward` par match gagné, paris sur le champion, arbre compact `tourneySnapshot()` dans l'historique), `clansEnd`, `goldEnd` et `coopEnd` (Boss, Donjon) déclenchent les récompenses dans `index.js` (jamais dans `battle.js`, qui ne connaît pas la base), puis règlement des paris et mise à jour des classements → `ended`.

## Invariants et pièges

- **Récompenses et événement `double`** : passe toujours par `scaled()` dans `index.js` ; ne crédite jamais directement `Rules.REWARDS` (modes PvP : ×3 et participation 100 XP ; les modes coopératifs et le Golden Shower utilisent `Rules.COOP_PARTICIPATION`, 25 XP). Les récompenses PvP ne dépendent plus de la puissance : l'équilibrage se fait au lancement dans `start()` de `battle.js` (bonus du plus faible `Rules.powerUnderdog`, champ `boost`, désactivé par `battle.balance = false` pour le duel d'entraînement ; équipe faible via `clanUnderdog` en Guerre des clans). Exception : les modes coopératifs (sans événement) créditent la récompense commune du résultat `coopEnd` à **tous** les participants humains, morts compris ; les kills de monstres ne rapportent rien et ne comptent pas dans le record.
- **Bots** (`bot: true`, clé `bot<n>`) et joueurs sans `userId` ne reçoivent rien et ne sont jamais sauvegardés ; on peut pourtant parier sur eux.
- **Clés de combattants** : `u<id>` pour un humain, `bot<n>` pour un bot ; les paris, le ciblage et les classements s'appuient dessus.
- **Zone et météores ne peuvent pas tuer le dernier survivant** ; si tous meurent le même tick, le dernier mort ressuscite à 1 PV et gagne. Les morts de zone/météore n'ont pas de tueur (pas de XP de kill).
- **Chance** : les % d'équipement s'*ajoutent* en points (pas de multiplication) ; plafond 200 pour la table de loot.
- **Tirages de loot/forge** : `crypto` (dans `game.js`). **Combat** : `Math.random`.
- **Mises** : retirées immédiatement du joueur et sauvegardées ; remboursées si la file est rouverte, l'arène réinitialisée, le combattant banni ou le serveur redémarré (`bets.refundAll()` au démarrage). L'état est dans `db.state.bets`.
- **Changement d'état d'un personnage** : passe par `action()` dans `index.js` (sauvegarde + événement `me`) ; les erreurs lancées par `game.js` deviennent des réponses 400 avec leur message en français.
- **Potions** : consommées au lancement (écouteur `battle.on('start')` dans `index.js`), jamais en entraînement ; une seule par partie, déclenchée au plus une fois (`potionUsed`).
- **Fantômes** (`ghost: true`) : comptes créés par `!join` sans compte, sans mot de passe, invisibles au login ; absorbés par `game.linkTwitch` → `absorbGhost`. Un nouveau champ de personnage doit aussi être fusionné dans `absorbGhost`.
- **Un seul processus** : l'état est en mémoire et la file/bataille aussi ; ne jamais faire tourner plus d'une machine (`fly.toml` : pas d'arrêt automatique, `fly deploy --ha=false`, volume `zer0loot_data` monté sur `/data`). `DATA_DIR` doit pointer vers un volume persistant en ligne.
- **Équipe en Guerre des clans** : portée par le participant (`clan`) et conservée au lancement malgré le recalcul des stats (`start()` la recopie après `refreshParticipant`) ; les paris d'équipe utilisent la clé `clan:rouge` / `clan:bleu`.
- **Sondage du donjon** : n'importe qui vote (chat : `chatCommand` dans `index.js`, exporté pour les tests ; site : `/api/poll/vote`), une voix par clé `t:<login Twitch>` ou `u:<id>` ; `battle.js` applique l'effet, `index.js` crédite golds / XP / coffres (événement `pollEnd`) à tous les participants humains.
- **Profils des joueurs** : le jeu est en ligne avec de vrais joueurs ; un changement de forme des données ne doit **jamais** effacer de progression. Tout nouveau champ passe par `upgrade()` et `test/migration.test.js` démarre le vrai serveur sur `test/fixtures/db-v1.json` (sauvegarde V1) pour le vérifier.
- **Mode Solo** : une partie en cours est marquée `soloActive` sur le personnage ; `refundSoloRuns()` (au chargement de `index.js`) rend l'énergie (ou la clé de boss) si le serveur a redémarré. Jamais de potion en solo. Les gains sont crédités par `soloRewards()` dans `index.js`.
- **Émeraudes** (`character.emeralds`) : gagnées au Survivor, par Mini Ether et dans les trésors de pêche ; dépensées en méta-progression du Survivor et à la Maison. Les améliorations du Survivor ne touchent jamais les autres modes.
- **Visage dessiné** : jamais envoyé dans les frames (seulement `app.drawing = "id.version"`), l'arène le charge via `GET /api/drawing/:id` (cache dans `fighter.js`).
- **Historique et statistiques** : `recordActivity()` (`game.js`) ajoute une ligne à `character.history` (50 au plus, photo du personnage) et met à jour `character.lifetime` (⚠️ `character.stats`, ce sont les points de caractéristiques). Appelé par `recordBattle()` dans les écouteurs de fin d'`index.js` et par `soloRewards()` ; les gains d'une partie du stream passent par `grantBattle()`. La bataille compte `taken` / `bossDealt` (dans `tally()`, à partir des événements `hit`), `hillTime` et `deaths`. Vues admin : `/api/admin/history` et `/api/admin/market/trades` (journal `db.state.market.trades`).
- **Ouverture de coffre** : décidée côté serveur dès l'appel `/api/chest/open` ; l'animation par clics (`public/js/chest.js`) est purement visuelle.
- **Familiers** : l'état est calculé paresseusement (`Rules.petAdvance`, même fonction dans le navigateur pour les barres en direct) ; seul le familier principal a des besoins qui baissent. Tirage du drop par `crypto` (`rollPetDrop`), appelé par `petDrop()` d'`index.js` (Combat de Boss, chaque boss du Boss Rush, Défi des boss). Le compagnon de combat passe dans les frames (`pet`) et se dessine avec `drawPet()` de `monsters.js`. L'onglet est dans `public/js/pets.js` (chargé avant `character.js`).

## Tests et garde-fous automatiques

- Un fichier de test par domaine dans `test/` (`combat`, `solo`, `rush`, `pets`, `casino`, `fishing`, `survivor`, `housing`, `history`, `migration`, `loot`, `chests`, `progression`, `stats`, `classes`, `battle`, `events`, `modes`, `bosses`, `koth`, `clans`, `gold`, `talents`, `consumables`, `presets`, `bets`, `forge`, `sets`, `achievements`, `appearance`) et `http.test.js` : tests d'intégration sur le vrai serveur Express (port aléatoire : comptes, rôles, file, paris, bans, liaison Twitch, bataille complète pilotée à la main). Runner natif de Node, aucune dépendance.
- **Chaque fichier de test commence par `require('./helpers')`** : il isole la base dans un dossier temporaire (`DATA_DIR`) avant que `server/db.js` soit chargé, et fournit `Rules`, `game`, `db`, `Battle`, `testBattle(fighters)` (bataille dont la boucle est arrêtée, on appelle `attack()`/`tick()` à la main) et `base()` (stats neutres).
- **Le nom de chaque test est préfixé par les identifiants de [SPECIFICATION.md](SPECIFICATION.md)** qu'il vérifie : `test('[BET-7] paris : …', …)`. Un nouveau comportement = une exigence dans la spec + un test tagué.
- `server/index.js` n'a plus d'effet de bord à l'import : il exporte `{ app, server, io, battle, bets, start }`, et `start()` (appelé seulement par `node server/index.js`) branche le chat Twitch, les minuteurs, les signaux et `listen`. Les tests importent le module et appellent `server.listen(0)`. Toute nouvelle chose à effet permanent (minuteur, connexion externe) va dans `start()`.
- Couverture (`npm run test:coverage`) : ~91 % des lignes ; `server/twitch.js` (chat, OAuth) et `public/` ne sont pas testés. **Couverture de la spec** : `npm run spec:coverage` liste les exigences de `SPECIFICATION.md` sans test ; `--json` pour un traitement automatique, `--strict` échoue s'il manque une exigence, un tag, ou s'il reste un test `skip`/`todo` (qui ne compte pas comme couverture). Une exigence marquée « (vérification manuelle) » dans la spec (interface, volume Fly.io…) n'est jamais comptée comme manquante.
- Hooks commités dans [.claude/settings.json](.claude/settings.json) (scripts dans `.claude/hooks/`) :
  - **PostToolUse (Edit|Write)** → `run-tests.js` : relance `npm test` quand un fichier de `server/`, `shared/` ou `test/` est modifié ; en cas d'échec le détail est renvoyé à Claude.
  - **Stop** → `check-done.js` : empêche de terminer (une fois par tour) si du code de `server/`/`shared/` a changé sans test ni mise à jour de `SPECIFICATION.md`, ou si `npm test` est rouge. La vérification se base sur `git status` : elle ne voit que les changements non commités.
